# 批准菜单变灰修复

用户现场截图显示旧申请的 client 标签仍在菜单中，但项目为灰色。代码路径说明：Native 只有 inbox_state=2 时允许菜单批准；人工接管/拒绝/截止会消费该申请，但 Broker 没有收到拒绝者的 client_id，可能仍维持 pending。菜单还保留上次 client 标签，造成“有申请却不能点击”的误导。打开终端右键菜单也会按人工优先策略撤销申请。

已修改：

1. `window.c` 在 Bridge 通知/250 ms 定时回调中调用 `ai_bridge_offer_pending`，有效申请直接打开非模态批准窗口。事件线程不等待用户或 MCP。
2. `bridge.c` 在状态回执中携带被拒绝申请的真实 client_id；拒绝不会误报成上一个已批准客户端。菜单无申请/已有窗口时更新为明确文本，去除陈旧请求标签。
3. Broker 接收拒绝后清理 pending 及 deadline，向同一客户端返回 rejected_locally，阻止轮询自动重新弹出。只有用户明确要求重试时，客户端先 release_control 再发新申请。
4. 测试前端与生产窗口共用 offer 函数；新增回归断言证明无需菜单点击即可打开窗口、拒绝后无陈旧锁、同一客户端不自动重提，其他客户端可发明确新请求。

修复版 Windows 编译及自动化回归结果见最新 rust-tests.txt 和 mcp-smoke-results.json。共 17 项 Rust 测试，加 Native 环形缓冲、命令校验、Shell 包装及 MCP 全链路回归。旧版及已运行进程不能热升级；使用修复目录的程序重新连接。并未移除本地批准，也未自动点击用户批准窗口。

现场 `df -h` 任务尚未在服务器成功执行；修复后的真实 SSH 验证仍需用户重新连接并批准测试。应用本身未改动远端状态。
